# 方案库：6 个可复用的 AI 落地模式

> `cases/` 记录**这一家做了什么**；`solutions/` 回答**这一类该怎么搭**。
> 6 个模式覆盖了本库全部 20 条案例。

---

## 先看这张表：你的场景该用哪个模式

| 你的场景 | 模式 | 一句话方案 |
|---|---|---|
| 员工/顾问找不到文档，找到了也不敢用 | [1 检索问答](01-retrieval-knowledge.md) | 混合召回 + 权限前置 + 强制引用，答不出来要敢拒答 |
| 专业人员的时间被文书吃掉 | [2 环境文书](02-ambient-documentation.md) | 听 → 结构化 → 写草稿到既有系统 → 人签，只做草稿 |
| 客服/售后量大，诉求能被 API 化 | [3 对话拦截](03-deflection-agent.md) | 动作分级（只读/可逆/涉钱/不可逆），能办事而不只是能回答 |
| 调度、补货、排班靠人拍脑袋 | [4 运营编排](04-ops-orchestration.md) | 先把对象建对，再谈算法；建议要能被一键否决 |
| 工程师写重复代码/配置 | [5 工程内嵌](05-embedded-codegen.md) | 长在既有工程软件里，靠编译/仿真挡错，AI 不碰执行器 |
| 全公司都要用，但没有明确任务 | [6 全员平台](06-employee-platform.md) | 买的是一万人的入口，难点在权限、数据边界和助手治理 |

**最常见的错配**：拿模式 6 去解模式 1 的问题——买一个全员平台，指望它顺便解决"文档找不到"。这两件事的架构、评测、责任人都不同。

## 跨模式的四条通则

把 20 条案例横向看完，有四条结论在每个模式里都成立：

### 1. 嵌进既有工作流，不要新开入口

摩根士丹利接进顾问写邮件的流程、舍弗勒接进 TIA Portal、ADT 接在既有 chat 与电话渠道、Lowe's 挂在店员手持终端。**用户会不会为了用它多开一个窗口？会，就已经失败了。**

### 2. AI 出草稿，人签署

病历、代码、客户答复、调度建议——四个模式全都有这道闸门。越过它，错误就变成记录、事故、客诉或停机。

### 3. 先定义分母，再谈成效

Intercom 在 2026-08-31 改了自己的分母（原文写着 "Resolution Rate: Will increase"）；摩根士丹利 ">98%" 的分母是顾问团队不是个人频次；美的同一年多口径。**指标不是自然现象，是被定义出来的。**

### 4. 效益归因是独立的难题

NHS 案例里，英国统计监管办公室要求官方加注"不能把改善归因于该平台"。技术上线、业务改善、因果归因是三件事。写案例时分开写，比合成一句"提效 X%"诚实得多。

## 怎么用这个方案库

| 你在做什么 | 建议顺序 |
|---|---|
| **写方案/投标** | 先按上表定位模式 → 读该模式的「组件与关键选择」和「集成点」→ 再去对应案例抄具体的规模与数字 |
| **做技术选型** | 读该模式的「组件与关键选择」表，重点看"常见错误"那一列 |
| **评估厂商** | 用该模式的「怎么评测」表反问供应商，尤其是分母与定义 |
| **复盘自己的项目** | 对照「真实失败模式」，看自己踩了哪条 |

---

**还有一层更重要的边界**：这 6 个模式是**架构层**，可以跨行业复用；但「派谁去、派多久、交付什么、什么时候能撤」不由架构决定。

医疗就是反例：病历文书和床位调度同属一个行业，前者 `none` 零驻场，后者必须 Palantir 驻场。差别在于 AI 的输出要不要改动别人已有的工作方式。完整判断见 [`findings/05-industry-is-the-constraint.md`](../findings/05-industry-is-the-constraint.md)。

## 边界说明（重要）

**方案库是模式归纳，不是任何单一客户的实现图纸。**

- 案例企业公开的通常是：买了谁的产品、覆盖多少人、大致什么场景、什么数字。
- 企业普遍**不公开**：分块策略、嵌入模型、提示词、重排器、编排框架、权限实现。
- 因此每个模式里的"关键选择"与"常见错误"，是按公开材料 + 同行业公开工程实践**还原的通用形态**，不代表案例企业的真实实现。
- 凡案例页 §4「落地方式」写明的技术栈，以案例页为准；两处冲突时以案例页为准。

这条边界不写清，方案库就会变成另一种"营销话术"——那正是本仓库想避免的东西。
