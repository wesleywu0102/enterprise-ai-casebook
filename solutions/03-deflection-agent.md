# 模式 3：一线对话的自动解决（Deflection Agent）

> 不只是回答"怎么改套餐"，而是**把它改掉**。能不能执行动作，是这条路线的分水岭。

| | |
|---|---|
| **典型输入** | 客户在 chat / 电话 / App 里的诉求 + 账户、订单、设备、账单上下文 |
| **典型输出** | 已完成的动作（改套餐、退款、预约、解锁）+ 转人工时带完整上下文 |
| **适用** | 诉求高频、政策清晰、动作可 API 化、错误可回滚 |
| **不适用** | 低量高价值诉求、政策需要临场判断、动作不可逆且金额大 |
| **本库案例** | [ADT](../cases/finance/adt-sierra-agent.md)、[Intercom Fin](../cases/software/intercom-fin.md)、[T-Mobile](../cases/telecom/tmobile-intentcx.md)、[Klarna（反例）](../cases/retracted/klarna-ai-assistant.md) |

---

## 1. 参考架构

```
客户发起（chat / 语音 / App）
  ↓
① 身份与上下文注入：账户、订单、设备状态、历史工单、账单
  ↓
② 意图识别 + 政策检索：这件事现在能不能办？（退款政策、挽留政策、合规限制）
  ↓
③ 动作层（关键分水岭）
     只读：查订单、查故障状态、解释账单
     可写：改套餐、重置密码、预约上门、发补货
  ↓
④ 结果判定：动作成功 / 需人工确认 / 高风险升级
  ↓
⑤ 转人工：必须带上完整上下文，不能让客户重讲一遍
  ↓
⑥ 质检与回捞：7 天内是否重复联系？ → 判定"假解决"
```

---

## 2. 组件与关键选择

| 层 | 做什么 | 关键选择 | 常见错误 |
|---|---|---|---|
| 上下文 | 一次会话内拿到全部相关状态 | 动作前重新拉一次实时状态，别用缓存 | 用 5 分钟前的余额做退款判断 |
| 政策层 | 把政策写成可执行规则 | 政策用结构化规则表达，LLM 只负责"选哪条" | 让 LLM 自由解释政策，退款口径每次不同 |
| 动作层 | 调 API 执行 | **按可逆性分级**：可逆全自动、不可逆要二次确认 | 一开始就做退款，出一次事故项目就停 |
| 转人工 | 交接 | 上下文 + AI 已试过的方案 + 建议动作 | 转过去只有一句"客户要退款" |
| 质检 | 事后抽样 | 用"7 天重复联系率"抓假解决 | 只看拦截率，越高越"成功" |

### 动作分级表（这是最该先画的一张表）

| 级别 | 例子 | 权限 |
|---|---|---|
| L1 只读 | 查订单、查设备状态 | 全自动 |
| L2 可逆小动作 | 改套餐、重置密码、发补货 | 全自动 + 事后抽检 |
| L3 可逆但涉及金额 | 退款、减免、补偿 | 阈值内自动，超阈值人工批 |
| L4 不可逆 | 销户、停服务 | 只做预填单，人执行 |

## 3. 集成点：成败在这里

- **ADT**：把 agent 接在 chat 与电话两条既有渠道上，不是新开入口。电话渠道拦截率（16%→25%）明显低于 chat（45%→60%）——因为口音、噪音、老年用户，语音不是"把 chat 加个 TTS"就能复用的。
- **T-Mobile**：AI 承接了 40% 的客户接触，人工通话量 -55%。注意这是集团口径（Deutsche Telekom 2026-10），没有基线也没有时间窗。

---

## 4. 人机分工

| 环节 | AI | 人 |
|---|---|---|
| 高频诉求全流程 | ✅ | 抽检 |
| 例外与投诉 | ❌ 判断情绪与例外 | ✅ 全部接管 |
| 高风险动作 | ⚠️ 只做预填 | ✅ 批准 |
| 政策变更 | ❌ | ✅ 改规则库 |

一条硬规则：**AI 不许自己改自己的政策。** 政策库必须由人维护版本。

## 5. 怎么评测（口径陷阱最密集的地方）

这是全库最该被引用的一个"换尺子"样本。Intercom 在 **2026-08-31** 自己改了分母，帮助中心原文写着：

> "Resolution Rate: **Will increase**, because Fin Constrained conversations are no longer counted in the denominator"

它连算例都给了：33% → 50%。同时「解决」的定义里包含 *Assumed Resolution*——客户看完答案直接关窗、没再追问，也算解决并计费。

| 要问的问题 | 为什么 |
|---|---|
| 分母是什么？ | 全部对话 / 可处理对话 / 转人工前的对话，差 20 个点 |
| "解决"谁定义？ | 客户确认？关窗推定？人工复核？ |
| 假解决率多少？ | 7 天内重复联系率是最硬的对照 |
| 分渠道吗？ | 语音的拦截率通常远低于 chat |
| 计费与指标是否同源？ | 按结果收费的厂商，有动机放宽"解决"的定义 |

**一条安全写法**：任何拦截率数字都必须带"分母 + 定义 + 时间窗"。缺一项就不要写进文章。

## 6. 真实失败模式

1. **假解决**：关窗算解决，客户第二天又来了，指标好看、成本没降。
2. **质量下滑后回退**：Klarna 从「相当于 700 名客服」到 CEO 承认过度依赖、重新招人——这是本库唯一一条 X 级回撤记录，写这个模式必须先看它。
3. **语音当 chat 做**：直接把文本 agent 套 TTS，电话场景失败率极高。
4. **转人工断链**：AI 试过什么人工看不见，客户要重讲一遍，体验比不用 AI 更差。
5. **按结果计费的成本反噬**：解决量越大付得越多，规模上去后单位成本未必下降。
