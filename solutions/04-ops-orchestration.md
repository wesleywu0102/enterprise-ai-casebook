# 模式 4：运营编排与决策优化（Ops Orchestration）

> 这类项目看起来像"数据平台"，实际交付物是**一个能算的决策**：这张床给谁、这批货调哪、这条线排什么。

| | |
|---|---|
| **典型输入** | EHR / ERP / WMS / POS / IoT 等多源运营数据 |
| **典型输出** | 调度建议、预警、工单、what-if 推演 |
| **适用** | 决策重复发生、有明确目标函数（利用率、周转、缺货率）、数据已可接入 |
| **不适用** | 数据治理尚未完成、目标函数说不清、一线不认算法建议 |
| **本库案例** | [Tampa General](../cases/healthcare/tampa-general-palantir.md)、[Cleveland Clinic](../cases/healthcare/cleveland-clinic-palantir.md)、[Walgreens](../cases/retail/walgreens-palantir.md)、[Wendy's/QSCC](../cases/retail/wendys-qscc-palantir.md)、[美的](../cases/manufacturing/midea-agents.md)、[NHS FDP](../cases/public-sector/nhs-fdp-palantir.md)、[DoD Maven](../cases/public-sector/dod-maven-smart-system.md) |

---

## 1. 参考架构

```
多源系统（EHR / ERP / WMS / POS / IoT / 外部数据）
  ↓
① 接入与清洗（ETL / 连接器）← 通常吃掉 60–80% 的项目时间
  ↓
② 语义层 / 本体：把"患者、床位、手术、订单、库存、产线"建成对象与关系
  ↓
③ 决策层（三种，可叠加）
     a. 规则：阈值报警、政策约束
     b. 优化求解：排班、路径、库存分配
     c. 预测：需求、住院时长、设备故障
  ↓
④ 应用层：调度台、看板、what-if 沙盘、移动端工单
  ↓
⑤ 一线确认 → 执行 → 结果回流（这一步决定模型能不能持续变好）
```

**② 是本模式的技术核心，也是最容易被低估的**：没有统一定义的对象（"一个床位"在多套系统里 ID 不同），后面所有算法都在沙子上盖楼。

---

## 2. 组件与关键选择

| 层 | 做什么 | 关键选择 | 常见错误 |
|---|---|---|---|
| 接入 | 打通源系统 | 优先做**读**，别一开始就想双向写回 | 第一期就要替换源系统，直接拖死 |
| 语义层 | 建对象与关系 | 用业务语言命名（"患者转运"而不是 "table_42"） | 只做数仓表，没有对象模型 |
| 决策 | 规则 / 优化 / 预测 | 先用规则跑通闭环，再上模型 | 上来就做深度学习，无法解释所以没人信 |
| 应用 | 交付给一线 | 嵌进一线已经在用的界面（调度台、手持机） | 新建一个大屏，好看但没人用 |
| 回流 | 记录"采纳/否决" | 把人的否决理由结构化存下来 | 不记录，模型永远不知道建议为什么没用 |

## 3. 集成点：成败在这里

**Walgreens 的扩张路径是本模式最好的模板**：10 家店（计划）→ 约 4,000 家店 / 8 个月。先在少数门店把闭环跑通，再复制。

**Tampa General 的做法是把工程师放进院里**。医院官方表述是 Palantir 的人 "embedded themselves within our organization"，媒体直接写 "forward-deployed engineers"。这是本库唯一能拿出发言记录的 FDE 型交付。

**反面教材是 NHS FDP**：数据平台建成了，合同 3.3 亿英镑 / 7 年，但英国统计监管办公室（OSR）2026-07 要求 NHS England 在公开材料中加注——**不能把改善归因于该平台**。平台存在 ≠ 效益可归因。

## 4. 人机分工

| 环节 | AI | 人 |
|---|---|---|
| 数据整合 | ✅ | ✅ 定义口径 |
| 生成建议 | ✅ | — |
| 采纳决策 | ⚠️ 可自动化的仅限低风险 | ✅ 护士长/店长/工段长 |
| 例外处置 | ❌ | ✅ |

一条从医疗案例里来的经验：**建议必须能被一键否决，并且否决理由被记录。** 否则一线会用脚投票，项目在三个月内静默死亡。

---

## 5. 怎么评测（这个模式最难）

三个结构性困难，写文章时都要交代：

1. **没有基线**。Tampa 的"安置耗时 -83%""脓毒症住院日 -30%"都没有对照期与统计口径，无法判断是工具效果还是季节性。
2. **无法归因**。NHS 那条监管意见就是明证：多家信托同时在改进，凭什么算给平台。
3. **多口径并存**。美的同一年给出 7 亿与 7.7 亿两个降本数字，2026 目标 8.8 亿。

可用的替代指标：**建议采纳率、决策耗时、例外数量、单位产出**——这些至少能被定义清楚。

---

## 6. 真实失败模式

1. **数据接入吃掉整个预算**：80% 时间在打通系统，业务侧等不到价值，项目被砍。
2. **大屏工程**：看板做得漂亮，但决策还是靠微信群。
3. **算法不可解释，一线不认**：尤其在医疗与工业，护士和工段长不会执行一个说不出理由的建议。
4. **效益无法归因 → 续约被质疑**：NHS 是最贵的例子。
5. **一次性定制，无法复制**：每个客户现场重做一遍，这正是 FDE 模式"不可线性扩张"的根源。

## 7. 对应案例

| 案例 | 场景 | 已披露成效 | 证据 |
|---|---|---|---|
| [Tampa General](../cases/healthcare/tampa-general-palantir.md) | 床位与容量调度、脓毒症预警 | 安置耗时 -83%；脓毒症住院日 -30%（无基线） | B |
| [Cleveland Clinic](../cases/healthcare/cleveland-clinic-palantir.md) | 虚拟指挥中心 | 容量测算 -75%；急诊滞留 -1h/人（仅厂商口径） | B |
| [Walgreens](../cases/retail/walgreens-palantir.md) | 补货/调拨/排班编排 | 10 店 → 约 4,000 店 / 8 个月；**无效益数字** | C |
| [Wendy's / QSCC](../cases/retail/wendys-qscc-palantir.md) | 供应链数字孪生 | 一次糖浆短缺：15 人一天 → 5 分钟（n=1） | C |
| [美的集团](../cases/manufacturing/midea-agents.md) | 排产、供应链、质检（2 万个智能体） | 2025 降本 7–7.7 亿元（多口径） | A |
| [英国 NHS FDP](../cases/public-sector/nhs-fdp-palantir.md) | 联邦数据平台 | 3.3 亿英镑 / 7 年；监管称**不能归因** | A |
| [DoD Maven](../cases/public-sector/dod-maven-smart-system.md) | 目标识别与情报融合 | 累计上限约 12.75 亿美元；2 万活跃用户 | A |

## 8. 边界说明

本模式横跨"数据平台"与"生成式 AI"两类项目，本库在案例页 §4 分别标注了 Foundry（传统数据平台）与 AIP（AI 平台），读的时候不要混为一谈——Wendy's 那份 2024-08 通稿原文用的是将来时 *will be moving onto AIP*，被大量媒体写成了"已上线见效"。
